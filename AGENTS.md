## Authorship

Matthieu Chane is responsible for this code and is its only author. Nothing committed or published
from this repository may name or credit an AI assistant or coding agent, in any form: no
`Co-Authored-By` or session trailers in commit messages, no "generated with" footers or links in
pull requests, issues, reviews or comments, no agent-specific files or folders (instruction files,
settings, plans), and no mention in code comments or docs. Commits are authored as
`Matthieu Chane <matthieu.chanewenc@gmail.com>`. These instructions live in this `AGENTS.md`.

One exception: the names of third-party coding tools used as **product data** (target identifiers
such as `claude-code` or `cursor`, the file names those tools read such as `CLAUDE.md` or
`GEMINI.md`, catalog entries and their URLs) are allowed in `packages/catalog`, its templates and
tests, and in user-facing copy. The same goes for LLM providers and their models used as product data
(provider kinds such as `anthropic` or `mistral`, their SDK packages and model names) in `packages/llm`,
the API's provider settings and their tests. They describe what the product generates for its users; they never
credit or attribute this repository's code. Agent-specific files themselves stay out of the repository:
`node scripts/check-agent-files.mjs` (run in CI) fails when one is tracked outside `packages/catalog`.

## Workflow

Every change is made in its own git worktree, on its own branch: create one before the first
edit (`git worktree add <path> -b <branch> origin/main`) and run every command from it. Never
create or switch branches in the main clone, which stays on `main`, and never edit files there.
Several tasks can then run side by side without touching each other's files.

## Conventions

Coreloom UML follows the same conventions as [coreloom](https://github.com/eldenn/coreloom),
the monorepo it was stripped down from, so pieces stay easy to move between
the two repos:

- All code and configuration files must always be written in English: comments, log/error messages, string literals, identifiers, scripts, and git hooks. Conversations may be in other languages, but anything committed to the codebase stays English-only.
- Always pin exact versions for tools and packages (mise.toml, package.json, Dockerfiles, etc.). Never use `latest`, `^`, `~`, or other floating/range specifiers — resolve the concrete version and write it.
- In `apps/api`, source filenames must be kebab-case and never contain an underscore (`_`); use a hyphen (`-`) instead. This overrides AdonisJS's default snake_case: after running `node ace make:*`, rename the generated file to kebab-case and fix its import path. Two exceptions, both forced by tooling that pattern-matches on the name: the leading `<timestamp>_` prefix on database migration files (generated by Ace), and the trailing `_job` on job classes under `app/**` (the `@nemoventures/adonis-jobs` worker discovers jobs by the exact `_job.{ts,js}` suffix) — the descriptive part of both must still be kebab-case (`<timestamp>_add-widgets-table.ts`, `send-welcome-email_job.ts`).
- In `apps/api`, `app/` is organized by domain, not by type. Each domain gets its own folder (e.g. `app/auth/`, `app/users/`, `app/health/`) containing type subfolders as needed (`controllers/`, `validators/`, `middleware/`, `models/`). Cross-cutting framework code (e.g. the exceptions handler) lives under `app/shared/`. Do not create top-level type folders like `app/controllers/` or `app/models/`. After running `node ace make:*`, move the generated file into the appropriate domain folder and fix its `#app/...` import path.
- In `apps/api`, do not hard-code literals that belong to a finite/well-known domain, are repeated, or whose meaning is not self-evident (HTTP status codes, database error codes, etc.). Define each such value set once as an `enum` or `as const` object — under `app/shared/<concept>/` when cross-cutting, otherwise in the owning domain — and reference it everywhere. Example: `HttpStatus` (`#app/shared/http/http-status`). Where AdonisJS already provides typed helpers (e.g. `response.ok()`, `response.created()`, `response.conflict()`), prefer those for runtime responses.
- In `apps/api`, name request and response shape definitions after their direction, **input** and **output**, not "validator" or "schema". A domain keeps them in `validators/<domain>-input.ts` (exporting `<action>Input`, e.g. `loginInput`, `registerInput`) and `validators/<domain>-output.ts` (exporting `<name>Output`, e.g. `userOutput`).
- In `apps/api`, build VineJS validators with `vine.create(...)`, never the deprecated `vine.compile(...)`.
- In `apps/api`, `app/architectures/` is the reference domain for a user-owned resource — copy it (model + migration, `architectures-input`/`architectures-output`, serializer, RESTful controller, owned-resource service, routes, functional specs) when adding a new one.
- In `apps/api`, `app/projects/` is the top-level container of an account's work: design artifacts (architectures and agent conventions today) belong to a project. Both are exceptions to "belongs to": their `project_id` is nullable, so one can stand outside any project and has its own page listing all of them (`/architectures`, `/agent-configs`); agent conventions stay at most one per project (unique `project_id`, 409 otherwise) and, outside a project, read from the owner's architectures that are outside any project too (`whereConfigArchitecture`). A new kind of artifact gets its own domain (copied from `app/architectures/`) with a non-null `project_id` FK to `projects` (`ON DELETE CASCADE`) next to its `user_id`, a `hasMany` on `Project`, a `withCount` in `ProjectsController.index` and a count in `ProjectOutput`, and checks that the target project is the caller's with `findOwnedProject` (404 otherwise). Keep `user_id` on the artifact: ownership stays a flat `assertOwner` check. No generic artifacts table.
- In `apps/api`, list endpoints paginate through `#app/shared/pagination/paginate` (`paginate(query, { page, perPage }, serialize)`), returning the stable `{ data, meta: { page, perPage, total, lastPage } }` shape — never Lucid's own paginator JSON. `perPage` defaults to `PAGINATION_DEFAULT_PER_PAGE` and is clamped to `PAGINATION_MAX_PER_PAGE` (both `as const` in that module); the `*-input` validator only rejects non-positive values. Compose the list output type as `Paginated<XOutput>`.
- In `apps/api`, resource ownership is enforced with `assertOwner(resource, user)` (`#app/shared/authorization/assert-owner`) — a flat `userId` check — followed by `response.notFound(...)` when it returns `false` (a non-owned resource reads as 404, not 403). No inline `resource.userId !== user.id` checks, and no `@adonisjs/bouncer` / policy classes yet.
- In `apps/api`, object storage goes through `@adonisjs/drive` (the `drive` service / `drive.use(<disk>)`), never a hand-rolled `@aws-sdk/client-s3` client. Disks are declared in `config/drive.ts` (`fs`, `s3`); the active one is picked by `DRIVE_DISK` (`fs` | `s3`, see `#app/shared/drive/drive-disk`). MinIO backs `s3` locally, a real S3/R2/Spaces bucket in prod.
- `packages/config` and `packages/auth-policy` are vendored copies of coreloom's — treat a needed change there as "change it in coreloom, then re-copy" rather than forking. Two packaging divergences are intentional and must survive a re-copy: every workspace package uses the `@coreloom-uml/*` scope (not `@coreloom/*`), and `auth-policy` is consumed straight from TypeScript source (`exports` → `./src/index.ts`, no `tsup` build). There is no `packages/ui`: the front end's components come from coreloom-ui (next rule).
- **Front end: coreloom-ui prevails.** Every component in `apps/web` comes from the coreloom-ui shadcn registry (`@coreloom/*` in `apps/web/components.json`, installed with `pnpm dlx shadcn@latest add @coreloom/<name>`), and its rules and stack win over anything else on the front: read `apps/web/AGENTS.md` and the coreloom-ui starter before changing the UI. A generic component the app is missing is added to coreloom-ui and installed from there, never written in `apps/web`. A front-end tool that duplicates or is not part of coreloom-ui's stack is removed (React Hook Form, i18next, Testing Library/jsdom, a second UI package, Biome on `apps/web` were removed for this reason). `apps/web` keeps coreloom-ui's versions (`package.json` pins, TypeScript 7 for `tsc` + `@typescript/typescript6` for ESLint, `tsconfig.json` options), its ESLint + Prettier setup (Biome only lints `apps/api` and the root), and Playwright + axe for screen tests. Registry files (`src/components/**`, `src/hooks/`, `src/lib/uml*`, `src/lib/{i18n,link,icon,utils,initials,ai}`) are left as installed and outside the app's lint; review upstream changes with `shadcn add @coreloom/<name> --diff` before `--overwrite`.
- **UML model and conversion: `packages/uml`.** The diagram model (`UmlSpec` + its zod schema) and its Mermaid, PlantUML and JSON reading and writing live in `packages/uml` (`@coreloom-uml/uml`), shared by `apps/web` and `apps/api`: `uml.ts`, `uml-elements.ts`, `uml-text.ts`, `uml-mermaid*.ts`, `uml-plantuml*.ts`, plus `index.ts` (`validateDiagram`, `parseDiagramText`, `formatDiagramText`, `detectDiagramTextFormat`). They came from coreloom-ui's registry, but they are this repo's code now: every change to the model or to a conversion is made there (with a test in `src/*.test.ts`), never in `apps/web` and never in coreloom-ui, which stays centred on the front end. The package depends on `zod` only — no React, no DOM, no rendering — and is consumed from TypeScript source like `auth-policy`, by Vite and by Node, so relative imports name the `.ts` file and only erasable TypeScript syntax is allowed (`erasableSyntaxOnly`). `apps/web/src/lib/` keeps only the front-end-only `uml-*` files (`uml-edit*`, `uml-graph*`, `uml-layout`, `uml-arrange`, `uml-image`, `uml-sequence`); registry components still import the shared ones as `@/lib/uml`, `@/lib/uml-mermaid`…, which `paths` in `apps/web/tsconfig.json` and `UML_SHARED` in `apps/web/vite.config.ts` resolve to `packages/uml/src` (keep both lists in sync). App code imports `@coreloom-uml/uml` directly. In `apps/api`, every save of a diagram's content goes through `app/diagrams/services/diagram-content.ts` (`checkDiagramValue` for JSON, `checkDiagramText` for Mermaid/PlantUML/JSON text): it checks the shared schema and the size limit, and a refusal is a 422 built with `invalidDiagram(problems)`. Never store content that skipped it. **After a `shadcn add … --overwrite`, delete any shared `uml-*` file the registry reinstalled under `apps/web/src/lib/`** (it would be dead code, shadowed by the alias), and port anything worth keeping from its diff into `packages/uml`.
- **Agent conventions catalog: `packages/catalog`.** `@coreloom-uml/catalog` holds everything the agent-conventions feature renders from: the questionnaires (`src/questionnaires/`, one file each, with their English fragments and `en`/`fr` labels), the slot registry (`src/slots.ts`), the sections (`src/sections.ts`), one template per target tool (`src/targets/`: its pointer and, where the tool can enforce something by itself, a `settings` file derived from slots through `TargetContext` — never from free text beyond the commands `splitCommands` lets through), model suggestions (`src/models.ts`) and `renderAgentContext` (`src/render/`), a pure function: same input, same bytes, no date, id or network. Packaged like `packages/uml` (zod only, TypeScript source, `.ts` imports, erasable syntax). `apps/api` and the CLI import it; `apps/web` gets questionnaires from the API, never by import. A question id is never reused, a slot is declared once and never renamed, and any change to a question, option or fragment bumps the questionnaire's `version`. Any change to what the catalog renders bumps `CATALOG_VERSION` (`src/version.ts`) together with the package's `version`, which a test keeps equal (the package is in the changesets `ignore` list). Each target template carries the date its tool's documentation was last checked (`verifiedOn`) and the pages read (`sources`): re-read them before relying on a tool's behaviour. The hand-picked skills (`src/skills-data.ts`, checked by `skillSchema` and matched by `matchSkills`) are links to third-party Agent Skills only, never an install command, each pinned to a tag or a commit, at most `SKILLS_MAX`, all with `origin: 'manual'`, added and checked by hand. Every slot affinity fits the question that feeds its slot, and every diagram affinity names `DIAGRAM_KINDS` (tests check both). The found skills live in the API's `skills` table (`origin = search`), never in the package: the weekly `RefreshSkillsJob` (`app/jobs/refresh-skills_job.ts`, scheduled by `node ace skills:setup`) runs `refreshCatalog` (`app/skills/services/skills-catalog.ts`), which keeps every skill `src/skill-search-plan.ts` finds and marks it eligible or not with a reason; change what it looks for in the plan, never a found skill by hand (block one with `node ace skills:block`). Suggestions read the package's skills plus the eligible, active rows (`suggestableSkills`). Only that job and `node ace skills:refresh` call skills.sh and GitHub; no request handler does. From the project's package diagrams, `renderDependencyCruiser` (`src/render/architecture-boundaries.ts`) also renders a `.dependency-cruiser.cjs` (kind `config`, a managed block in `SLASH_MARKERS`) whose `forbidden` rules refuse the dependencies no arrow draws, and adds the command that checks it to the `Architecture` section. A diagram holds no folder path, so a package's name is read as its folder from the repository root, under its parent package's folder when nested; a package whose name is not a plain folder path is left out, a diagram without an arrow between two folders too, and other diagram kinds are not read. Generated files themselves are never committed here (see Authorship). In `apps/api`, the `app/agent-configs/` domain stores what the files are rendered from (questionnaires, answers, accepted rules, notes, targets) and immutable generations; every render goes through `render` in `app/agent-configs/services/agent-context.ts` (current catalog, answers migrated first), and every change to that source bumps the configuration's `revision` (`bumpRevision`). Never store or edit a generated file outside a generation, and never let an input carry `MARKER_PREFIX`.
- **CLI: `apps/cli`.** `@coreloom-uml/cli` is the only package published to npm (`publishConfig.access: public`, versioned on its own outside the changesets `fixed` group, published by `changesets.yml` when `NPM_TOKEN` exists). It is bundled by tsup into one ESM file for Node 22+; `@coreloom-uml/catalog` (a devDependency) and zod are bundled in, so its runtime dependencies stay `citty` and `@clack/prompts`, and it never imports `apps/api` or `ai`. It authenticates with an account API key (`clu_…`, `read` is enough) read from `CORELOOM_UML_API_KEY` or the user config file written by `config set-key` (mode 0600), never from an argument or the manifest; there is no default API URL. It writes only the managed block (`findManagedBlock`/`hashManagedBlock` from the catalog; `#` markers at the top of a TOML settings file, `//` markers in a `.cjs` configuration file) or, in a JSON settings file, only the entries the generation lists, recorded in the manifest (`src/json-settings.ts`), asks before any change to a settings or `.cjs` file, checks every path the API sends (relative, normalized, inside the working directory, no symbolic link), and leaves a block edited by hand alone unless told otherwise (exit code 2). Everything it prints or asks goes through `Io` (`src/io.ts`) so commands are tested as functions, against a fixture HTTP server and a temporary folder.
- **Calls with the user's own LLM key or subscription: `packages/llm`.** `@coreloom-uml/llm` wraps the Vercel AI SDK (`ai` 7 and the `@ai-sdk/*` providers, exact versions) for the agent-conventions feature: building a model from the browser's provider settings (`createLanguageModel`, redirects never followed), the base URL allowlist (`baseUrlProblem`, from `LLM_ALLOWED_BASE_URLS` in `config/llm.ts`), the connection test and the rule proposals (structured output, then cleaned and deduplicated), and the two subscription models: `openai-codex` (ChatGPT, OpenAI's device code, `codex.ts`) and `claude-code` (Claude, through the `claude` binary, `claude-code.ts`). Packaged like `packages/catalog` (TypeScript source, `.ts` imports); the CLI does not depend on it. API keys stay in the browser only: a key arrives in the request body, is passed to `LanguageModels.create` (`app/llm/services/language-models.ts`) and dropped — never stored, logged, traced, returned or put in an error. The only stored LLM secrets are ChatGPT subscription tokens, encrypted with `APP_KEY` in `llm_connections` (`app/llm-connections/`), under the same never-returned/logged/traced rule. Claude credentials are never handled by our code: only the unmodified `claude` binary (pinned in the API image) holds them, in its own `CLAUDE_CONFIG_DIR` per account; no OAuth flow of ours, and nothing that poses as Claude Code (client id, identity prompt, User-Agent, billing header). Each subscription kind is behind its feature flag, and every call resolves its credential through `resolveCredential` (`app/llm-connections/services/llm-credential.ts`). Every provider failure is reduced to a `LlmFailureReason` before it is logged or answered (502 `{ reason }`). Tests never call a provider: they swap `LanguageModels`, `CodexOAuth` (a fake OAuth server) and `ClaudeCodeCli` (a fake binary) in the container. In `apps/web`, the provider and its key (none for a subscription) live only in the browser (`localStorage` key `llm-provider`, read and written through `src/lib/llm-provider.ts`) and travel only in the body of those calls; the provider kinds, their model suggestions and the allowed origins come from `GET /llm/providers`, never from importing the catalog.
- **Feature flags: `packages/feature-flags`.** `@coreloom-uml/feature-flags` declares every flag (`FEATURE_FLAGS`, keys in `FeatureFlagKey`, a default state each) and evaluates one (`evaluateFeatureFlag`, ported from coreloom-ui's `feature-flag-rules.tsx`: keep them in step). Packaged like `packages/uml` (zod only, TypeScript source, `.ts` imports, erasable syntax), in the changesets `ignore` list. A flag is declared in code, never created from the UI; the admin only edits its state. The admin is the default account (`isDefaultAccount`, `DEFAULT_ACCOUNT_EMAIL`): `middleware.admin()` (after `middleware.auth()`) answers 404 to everyone else. In `apps/api`, the states and their history live in `feature_flags` / `feature_flag_changes` and go through `app/feature-flags/services/feature-flags.ts` (`isFeatureEnabled(key, user)` to enforce a flag — a route behind an off flag answers 404 —, `updateFlag` to change one with a history line). In `apps/web`, read a flag with `useFeature(key)` (`src/lib/feature-flags.ts`, from `GET /features`); it only hides what the API already refuses. The single environment is `FEATURE_FLAG_ENVIRONMENT` (`instance`).
- **MCP server: `app/mcp/`.** `/mcp` (`apps/api`) is a Model Context Protocol endpoint for coding agents, built on `@modelcontextprotocol/sdk` (Streamable HTTP, stateless, JSON answers: one `McpServer` and one transport per request, see `mcp-controller.ts`). API tokens only (`guards: ['api']`), behind the `mcp-server` flag (404 while off); the controller checks the `read` ability itself, since every MCP call is a POST and `tokenAbility` reads the method. The tools (`services/mcp-server.ts`, names in `McpTool`, zod argument shapes in `validators/mcp-input.ts`) only read, and only what the token's account owns: something that isn't the caller's is a `not found` tool error. A tool that writes would need the `write` ability and must store a proposal for the owner to review, never apply it. The catalog only recommends how to register the server in each tool (`packages/catalog/src/targets/mcp.ts`); it never renders a tool's MCP settings file.
- `apps/web` talks to the API through the Tuyau typed client (`apps/web/src/lib/client.ts`), whose types come from `@coreloom-uml/api/registry` — generated into `apps/api/.adonisjs/client/registry/` by the assembler hooks in `apps/api/adonisrc.ts` on `node ace serve` / `pnpm dev`. That directory is committed (git-tracked despite `.adonisjs/` being ignored) so `check-types` is deterministic without a prior dev-server run; regenerate and commit it whenever routes, Vine input validators, or controller response shapes change. Return responses from controllers with the typed helpers (`response.ok`, `response.created`, `response.badRequest`, …), never `response.status(x).json(...)`, or the generated response/error types will be wrong.
- In `apps/web`, anything that varies per deployment (currently just the API URL) is resolved at **runtime**, not from `import.meta.env.VITE_*` at build time. The container entrypoint (`apps/web/docker/30-render-env-js.sh`) writes `$API_URL` into `/env.js`, loaded by `index.html` before the bundle; `client.ts` reads `window.__APP_CONFIG__.apiUrl` first, then falls back to `import.meta.env.VITE_API_URL` (dev only), then localhost. Add new runtime settings to all four spots (`public/env.js`, the entrypoint, the `Window` type in `vite-env.d.ts`, the reader) — do not reintroduce build-time `VITE_*` for deploy-varying values.
- In `apps/web`, all API reads and writes go through TanStack Query hooks (`useQuery` / `useMutation`) that wrap the Tuyau `client` — never raw `fetch` or `useEffect` data loading. One exception: a Server-Sent Events stream, which Tuyau cannot open, is read with an `EventSource` in a hook that only invalidates queries when an event arrives (`useSkillsLiveUpdates` in `apps/web/src/lib/skills.ts` is the reference); the data itself still comes through the query hooks. The shared `QueryClient` and the canonical hook pattern to copy live in `apps/web/src/lib/query.ts`; `apps/web/src/auth/auth-context.tsx` is the live reference (`useQuery` for `GET /auth/me`, `useMutation` for login/register/logout, `refresh` = `invalidateQueries`). Its `useAuth()` return surface (`user`, `isLoading`, `login`, `register`, `logout`, `refresh`) is a stable contract — keep it.
- In `apps/web`, forms use TanStack Form through coreloom-ui's `useAppForm` (`@/components/ui/form`: `form.AppField` + `field.TextField` / `PasswordField` / `SelectField`…, `form.SubmitButton`), validated with a `zod` schema in `validators.onSubmit`. Password length comes from `@coreloom-uml/auth-policy` (`PASSWORD_POLICY.minLength`). A page that delegates to a coreloom-ui block (`LoginForm`, `SignupForm`, `PasswordResetForm`, `SettingsSection`…) passes props in and leaves the block's own field handling alone.
- In `apps/web`, every user-facing string the app adds lives in `apps/web/src/messages.ts` (`en` is the source of truth and defines the `Messages` type; `fr` is translation data, so the English-only rule does not apply to its values) and is read with `const t = useT()` (`@/lib/locale`). Components' built-in strings come from coreloom-ui's `CoreloomI18nProvider`, which `LocaleProvider` feeds with the same locale (`useCoreloomI18n().messages` for things like `diagram.kinds`). No literal copy in JSX, no i18next. The language is a browser preference in `localStorage`, not deploy config.
- `apps/api` observability is OpenTelemetry → SigNoz in `apps/api/instrumentation.ts`, loaded before everything else via `node --import ./instrumentation.js` (prod `start` script + Dockerfile `CMD`) and re-imported in `bin/server.ts` for the shutdown flush. It reads the standard `OTEL_*` variables straight from `process.env` (it runs before `start/env.ts`), and is a no-op unless `OTEL_EXPORTER_OTLP_ENDPOINT` is set — so do **not** add `OTEL_*` to `start/env.ts`.
- The staging Coolify stack (`infra/docker-compose.staging.yml`) bundles a self-hosted SigNoz (`signoz-clickhouse` / `signoz-zookeeper` / `signoz` / `signoz-otel-collector` + migrators); the `api` service exports to `signoz-otel-collector:4318` over the Compose network. `infra/signoz/*` is a vendored copy from SigNoz `deploy/` at tag `v0.128.0` (the last tag with a Compose manifest) — re-copy from that tag rather than hand-editing. Divergences to preserve on re-copy: `cluster.xml` and `otel-collector-config.yaml` point at the `signoz-clickhouse` / `signoz-zookeeper` service names instead of upstream's `clickhouse` / `zookeeper-1` (each file has a header comment saying so). Keep the four image pins in the compose file in sync with that tag's manifest.
- Security headers: `@adonisjs/shield` (`apps/api/config/shield.ts`) for the API — `xFrame`/`hsts`/`contentTypeSniffing` on, `csp`/`csrf` intentionally off (JSON API; CORS allowlist + forced JSON preflight is the CSRF boundary). The SPA's `Content-Security-Policy` and hardening headers live in `apps/web/docker/nginx.conf.template`, where `${API_URL}` scopes `connect-src`.
- Email addresses are case-insensitive: `users.email` is `citext` (migration `1714000002000`) and every VineJS email input ends with `.toLowerCase()`. Keep both in sync — new email fields get `.toLowerCase()`, and don't reintroduce a plain `varchar` email column.
- `middleware.verified()` (`apps/api/app/auth/middleware/verified-middleware.ts`, registered in `start/kernel.ts`) gates a route behind a verified email — chain it after `middleware.auth()`. Nothing uses it yet; wire it onto routes that need it rather than re-checking `emailVerifiedAt` inline.
- Outbound transactional email is always `mail.sendLater(...)`, never `mail.send(...)`, so SMTP latency/failures never block or fail the request. `apps/api/start/mail.ts` registers a `mail.setMessenger` that turns every `sendLater` into a `SendMailJob` on the BullMQ queue — the send is retried on failure, visible/replayable in bull-board, and `SendMailJob.onFailed` logs a send that exhausts its retries. Do not add per-call-site `try/catch` + `logger.error`, and do not reach for `mail.send()` in a controller.
- File uploads go through `@adonisjs/drive` (never the DB, never the public filesystem), validated for MIME/extension **and** size at the boundary via `request.file(field, { size, extnames })` + `file.isValid`/`file.errors` → 422 — see `apps/api/app/account/controllers/avatar-controller.ts`, allowlist + max size as an `as const` in `app/account/constants/avatar.ts`. The disk is `private`: serve private objects back through an authenticated route that streams `disk.getStream(key)` with the right `Content-Type` (e.g. `GET /account/avatar`), not a signed URL. `serializeUser` stays **synchronous** and returns that stable relative path (`avatarUrl: user.avatarKey ? '/account/avatar' : null`) — do not make it async to build a signed URL.
- Background work runs on a BullMQ queue via `@nemoventures/adonis-jobs` (Redis-backed; `config/queue.ts` + `config/redis.ts`). Job classes live in `app/jobs/*_job.ts` (`node ace make:job`, one `default`-exported class extending `Job<Data, Return>` with a `process()` method), dispatched with `SomeJob.dispatch(data)` from a controller/service and executed by the `queue:work` worker (its own process — `pnpm --filter @coreloom-uml/api queue:work` locally, the `queue-worker` service in staging). `apps/api/app/jobs/example_job.ts` is the reference — copy it. Inspect / retry / remove jobs in `bull-board` (`http://localhost:8082` in dev). `apps/api/start/mail.ts` already routes `mail.sendLater(...)` onto this queue via `SendMailJob`, so transactional email is queued end to end.

## Scope

One gap is intentional and documented in the README's "Not yet included" section — do not treat it as a bug to fix unprompted:

- `apps/web` has no screen tests yet: they will be Playwright + axe, as in coreloom-ui (Vitest runs only Node unit tests of `src/**/*.test.ts`, with `passWithNoTests: true`). `apps/api` (Japa) is covered.
