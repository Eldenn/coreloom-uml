## Authorship

Matthieu Chane is responsible for this code and is its only author. Nothing committed or published
from this repository may name or credit an AI assistant or coding agent, in any form: no
`Co-Authored-By` or session trailers in commit messages, no "generated with" footers or links in
pull requests, issues, reviews or comments, no agent-specific files or folders (instruction files,
settings, plans), and no mention in code comments or docs. Commits are authored as
`Matthieu Chane <matthieu.chanewenc@gmail.com>`. These instructions live in this `AGENTS.md`.

One exception: the names of third-party coding tools used as **product data** (target identifiers
such as `claude-code` or `cursor`, the file names those tools read such as `CLAUDE.md` or
`GEMINI.md`, catalog entries and their URLs) are allowed in `packages/catalog`, its templates and
tests, and in user-facing copy. The same goes for LLM providers and their models used as product data
(provider kinds such as `anthropic` or `mistral`, their SDK packages and model names) in `packages/llm`,
the API's provider settings and their tests. They describe what the product generates for its users; they never
credit or attribute this repository's code. Agent-specific files themselves stay out of the repository:
`node scripts/check-agent-files.mjs` (run in CI) fails when one is tracked outside `packages/catalog`.

## Workflow

Every change is made in its own git worktree, on its own branch: create one before the first
edit (`git worktree add <path> -b <branch> origin/main`) and run every command from it. Never
create or switch branches in the main clone, which stays on `main`, and never edit files there.
Several tasks can then run side by side without touching each other's files.

## Conventions

Coreloom UML follows the same conventions as [coreloom](https://github.com/eldenn/coreloom),
the monorepo it was stripped down from, so pieces stay easy to move between
the two repos:

- All code and configuration files must always be written in English: comments, log/error messages, string literals, identifiers, scripts, and git hooks. Conversations may be in other languages, but anything committed to the codebase stays English-only.
- Always pin exact versions for tools and packages (mise.toml, package.json, Dockerfiles, etc.). Never use `latest`, `^`, `~`, or other floating/range specifiers — resolve the concrete version and write it.
- In `apps/api`, source filenames must be kebab-case and never contain an underscore (`_`); use a hyphen (`-`) instead. This overrides AdonisJS's default snake_case: after running `node ace make:*`, rename the generated file to kebab-case and fix its import path. Two exceptions, both forced by tooling that pattern-matches on the name: the leading `<timestamp>_` prefix on database migration files (generated by Ace), and the trailing `_job` on job classes under `app/**` (the `@nemoventures/adonis-jobs` worker discovers jobs by the exact `_job.{ts,js}` suffix) — the descriptive part of both must still be kebab-case (`<timestamp>_add-widgets-table.ts`, `send-welcome-email_job.ts`).
- In `apps/api`, `app/` is organized by domain, not by type. Each domain gets its own folder (e.g. `app/auth/`, `app/users/`, `app/health/`) containing type subfolders as needed (`controllers/`, `validators/`, `middleware/`, `models/`). Cross-cutting framework code (e.g. the exceptions handler) lives under `app/shared/`. Do not create top-level type folders like `app/controllers/` or `app/models/`. After running `node ace make:*`, move the generated file into the appropriate domain folder and fix its `#app/...` import path.
- In `apps/api`, do not hard-code literals that belong to a finite/well-known domain, are repeated, or whose meaning is not self-evident (HTTP status codes, database error codes, etc.). Define each such value set once as an `enum` or `as const` object — under `app/shared/<concept>/` when cross-cutting, otherwise in the owning domain — and reference it everywhere. Example: `HttpStatus` (`#app/shared/http/http-status`). Where AdonisJS already provides typed helpers (e.g. `response.ok()`, `response.created()`, `response.conflict()`), prefer those for runtime responses.
- In `apps/api`, name request and response shape definitions after their direction, **input** and **output**, not "validator" or "schema". A domain keeps them in `validators/<domain>-input.ts` (exporting `<action>Input`, e.g. `loginInput`, `registerInput`) and `validators/<domain>-output.ts` (exporting `<name>Output`, e.g. `userOutput`).
- In `apps/api`, build VineJS validators with `vine.create(...)`, never the deprecated `vine.compile(...)`.
- In `apps/api`, `app/architectures/` is the reference domain for a user-owned resource — copy it (model + migration, `architectures-input`/`architectures-output`, serializer, RESTful controller, owned-resource service, routes, functional specs) when adding a new one.
- In `apps/api`, `app/projects/` is the top-level container of an account's work: design artifacts (architectures and agent conventions today) belong to a project. Both are exceptions to "belongs to": their `project_id` is nullable, so one can stand outside any project and has its own page listing all of them (`/architectures`, `/agent-configs`); agent conventions stay at most one per project (unique `project_id`, 409 otherwise) and, outside a project, read from the owner's architectures that are outside any project too (`whereConfigArchitecture`). A new kind of artifact gets its own domain (copied from `app/architectures/`) with a non-null `project_id` FK to `projects` (`ON DELETE CASCADE`) next to its `user_id`, a `hasMany` on `Project`, a `withCount` in `ProjectsController.index` and a count in `ProjectOutput`, and checks that the target project is the caller's with `findOwnedProject` (404 otherwise). Keep `user_id` on the artifact: ownership stays a flat `assertOwner` check. No generic artifacts table.
- In `apps/api`, list endpoints paginate through `#app/shared/pagination/paginate` (`paginate(query, { page, perPage }, serialize)`), returning the stable `{ data, meta: { page, perPage, total, lastPage } }` shape — never Lucid's own paginator JSON. `perPage` defaults to `PAGINATION_DEFAULT_PER_PAGE` and is clamped to `PAGINATION_MAX_PER_PAGE` (both `as const` in that module); the `*-input` validator only rejects non-positive values. Compose the list output type as `Paginated<XOutput>`.
- In `apps/api`, resource ownership is enforced with `assertOwner(resource, user)` (`#app/shared/authorization/assert-owner`) — a flat `userId` check — followed by `response.notFound(...)` when it returns `false` (a non-owned resource reads as 404, not 403). No inline `resource.userId !== user.id` checks, and no `@adonisjs/bouncer` / policy classes yet.
- In `apps/api`, object storage goes through `@adonisjs/drive` (the `drive` service / `drive.use(<disk>)`), never a hand-rolled `@aws-sdk/client-s3` client. Disks are declared in `config/drive.ts` (`fs`, `s3`); the active one is picked by `DRIVE_DISK` (`fs` | `s3`, see `#app/shared/drive/drive-disk`). MinIO backs `s3` locally, a real S3/R2/Spaces bucket in prod.
- `infra/e2b/` (`compose.yaml` and `.env`) is a vendored copy of E2B Embed from e2b-dev/runtime at one commit (named in both headers): the self-hosted sandboxes of the code maps from GitHub, of the assistant's repository tools and of the web research, started on demand and never part of `infra/docker-compose.yml`. Re-copy both files from one commit rather than hand-editing; the only divergence to preserve is the four moved host ports listed in `compose.yaml`'s header. After a re-copy, start it and read a page through `ResearchSandbox` before relying on it.
- `packages/config` and `packages/auth-policy` are vendored copies of coreloom's — treat a needed change there as "change it in coreloom, then re-copy" rather than forking. Two packaging divergences are intentional and must survive a re-copy: every workspace package uses the `@coreloom-uml/*` scope (not `@coreloom/*`), and `auth-policy` is consumed straight from TypeScript source (`exports` → `./src/index.ts`, no `tsup` build). There is no `packages/ui`: the front end's components come from coreloom-ui (next rule).
- **Front end: coreloom-ui prevails.** Every component in `apps/web` comes from the coreloom-ui shadcn registry (`@coreloom/*` in `apps/web/components.json`, installed with `pnpm dlx shadcn@latest add @coreloom/<name>`), and its rules and stack win over anything else on the front: read `apps/web/AGENTS.md` and the coreloom-ui starter before changing the UI. A generic component the app is missing is added to coreloom-ui and installed from there, never written in `apps/web`. A front-end tool that duplicates or is not part of coreloom-ui's stack is removed (React Hook Form, i18next, Testing Library/jsdom, a second UI package, Biome on `apps/web` were removed for this reason). `apps/web` keeps coreloom-ui's versions (`package.json` pins, TypeScript 7 for `tsc` + `@typescript/typescript6` for ESLint, `tsconfig.json` options), its ESLint + Prettier setup (Biome only lints `apps/api` and the root), and Playwright + axe for screen tests. Registry files (`src/components/**`, `src/hooks/`, `src/lib/uml*`, `src/lib/{i18n,link,icon,utils,initials,ai}`) are left as installed and outside the app's lint; review upstream changes with `shadcn add @coreloom/<name> --diff` before `--overwrite`.
- **UML model and conversion: `packages/uml`.** The diagram model (`UmlSpec` + its zod schema) and its Mermaid, PlantUML and JSON reading and writing live in `packages/uml` (`@coreloom-uml/uml`), shared by `apps/web` and `apps/api`: `uml.ts`, `uml-elements.ts`, `uml-text.ts`, `uml-mermaid*.ts`, `uml-plantuml*.ts`, plus `index.ts` (`validateDiagram`, `parseDiagramText`, `formatDiagramText`, `detectDiagramTextFormat`). They came from coreloom-ui's registry, but they are this repo's code now: every change to the model or to a conversion is made there (with a test in `src/*.test.ts`), never in `apps/web` and never in coreloom-ui, which stays centred on the front end. The package depends on `zod` only — no React, no DOM, no rendering — and is consumed from TypeScript source like `auth-policy`, by Vite and by Node, so relative imports name the `.ts` file and only erasable TypeScript syntax is allowed (`erasableSyntaxOnly`). `apps/web/src/lib/` keeps only the front-end-only `uml-*` files (`uml-edit*`, `uml-graph*`, `uml-layout`, `uml-arrange`, `uml-route`, `uml-image`, `uml-sequence`); registry components still import the shared ones as `@/lib/uml`, `@/lib/uml-mermaid`…, which `paths` in `apps/web/tsconfig.json` and `UML_SHARED` in `apps/web/vite.config.ts` resolve to `packages/uml/src` (keep both lists in sync). App code imports `@coreloom-uml/uml` directly. In `apps/api`, every save of a diagram's content goes through `app/diagrams/services/diagram-content.ts` (`checkDiagramValue` for JSON, `checkDiagramText` for Mermaid/PlantUML/JSON text): it checks the shared schema and the size limit, and a refusal is a 422 built with `invalidDiagram(problems)`. Never store content that skipped it. **After a `shadcn add … --overwrite`, delete any shared `uml-*` file the registry reinstalled under `apps/web/src/lib/`** (it would be dead code, shadowed by the alias), and port anything worth keeping from its diff into `packages/uml`.
- **Agent conventions catalog: `packages/catalog`.** `@coreloom-uml/catalog` holds everything the agent-conventions feature renders from: the rule packs (`src/rule-packs/`, one file each: groups of ready-made rules, one group per slot, with their English lines and `en`/`fr` labels), the slot registry (`src/slots.ts`), the sections (`src/sections.ts`), one template per target tool (`src/targets/`: its pointer and, where the tool can enforce something by itself, a `settings` file derived from slots through `TargetContext` — never from free text beyond the commands `splitCommands` lets through), model suggestions (`src/models.ts`) and `renderAgentContext` (`src/render/`), a pure function: same input, same bytes, no date, id or network. Besides each tool's files it renders the gates that hold whatever the tool (`src/render/gates.ts`): Git hooks in `.githooks/` and, only when the `git.ci-workflow` rule `github-actions` is held, the `.github/workflows/agent-conventions.yml` workflow, both in `#` markers. A gate enforces only what a ready-made rule states without ambiguity, runs only commands `splitCommands` kept, and pins every action by commit and every downloaded binary by version and checksum: re-check those pins when raising them. Packaged like `packages/uml` (zod only, TypeScript source, `.ts` imports, erasable syntax). `apps/api` and the CLI import it; `apps/web` gets the rule packs from the API, never by import. A configuration holds ready-made rules (`AcceptedRule`: a slot, a rule id and, for an `input` rule, the typed text), checked with `acceptedProblem` before they are stored; there is no questionnaire and no answer. A rule id is never reused within its slot, and a slot is declared once and never renamed. `APPLIED_RULES` (`src/ready-rules.ts`) lists the only rules the renderer derives a file from besides AGENTS.md (the renderer can read no other slot), and the screen marks them: keep it true when a renderer starts or stops reading a rule. Any change to what the catalog renders bumps `CATALOG_VERSION` (`src/version.ts`) together with the package's `version`, which a test keeps equal (the package is in the changesets `ignore` list). Each target template carries the date its tool's documentation was last checked (`verifiedOn`) and the pages read (`sources`): re-read them before relying on a tool's behaviour. `pnpm --filter @coreloom-uml/catalog test:e2e` (`packages/catalog/e2e/`, run in CI, offline) loads the rendered settings into the tools themselves and checks them against the vendored settings schemas: add a case there for any new claim about what a settings file does. It also runs the rendered Git hooks on real commits and reads the rendered workflow as YAML (action pins, the guarded check step). Codex and Claude Code are not dependencies: the CI job installs them at exact versions (keep Claude Code's equal to the API image's), the suite finds them on `PATH` or through `CODEX_BIN` / `CLAUDE_BIN`, skips their cases when one is missing locally and fails when one is missing in CI. The hand-picked skills (`src/skills-data.ts`, checked by `skillSchema` and matched by `matchSkills`) are third-party Agent Skills, each pinned to a tag or a commit, at most `SKILLS_MAX`, all with `origin: 'manual'`, added and checked by hand. Every slot affinity names rules of the group that feeds its slot, and every diagram affinity names `DIAGRAM_KINDS` (tests check both). Tags (`Topic`, `src/topics.ts`) cross the three: a ready-made rule has its slot's (`slotTopics`: its prefix's in `SLOT_PREFIX_TOPICS`, plus its own in `SLOT_TOPICS`; a test keeps every prefix listed), a skill has the topics of the queries that found it (or none, by hand), a ready-made role has its tags in `PRESET_TOPICS`, set by hand from its mission (none for a stack or trade the packs do not cover; a test fails while a preset is missing, so re-read them at every copy of agency-agents). Tags are a weak signal: in `matchSkills` a shared tag makes a skill compatible, never conflicting, after the affinities; `suggestRoles` suggests the roles sharing tags with the rules held (`heldTopics`), each with the skills sharing its own (`GET /agent-configs/:id/roles/suggestions`, behind `agent-roles`). The found skills live in the API's `skills` table (`origin = search`), never in the package: the weekly `RefreshSkillsJob` (`app/jobs/refresh-skills_job.ts`, scheduled by `node ace skills:setup`) runs `refreshCatalog` (`app/skills/services/skills-catalog.ts`), which keeps every skill `src/skill-search-plan.ts` finds and marks it eligible or not with a reason; change what it looks for in the plan, never a found skill by hand (block one with `node ace skills:block`). Suggestions read the package's skills plus the eligible, active rows (`suggestableSkills`). A skill's files may be installed in the repositories of the accounts that hold it, so they are copied and read first: after each refresh, `captureSkillVersions` (`app/skills/services/skill-versions.ts`) copies the folder of every skill that may be suggested at the commit its URL pins, once per content SHA, into `skill_versions` (the list of files) and Drive (the files, gzipped, `skill-versions/<slug>/<sha>.json.gz`, never rewritten): text files only, no symbolic link or submodule, within `SKILL_VERSION_LIMITS`, under a licence of `OPEN_LICENSES` (a licence file of the folder, else the repository's, added as `LICENSE`, else the `license:` of SKILL.md). A new copy is `pending`; the admin reads it on `/skill-versions` (`/admin/skill-versions`, `middleware.admin()`), file by file against the newest approved copy of the same skill, and approves or rejects it. Only an approved copy is ever installed, and an agent follows it as instructions and may run its scripts: never approve one unread. Before the admin may approve a copy, SkillSpector must have scanned it whole and not recommend `DO_NOT_INSTALL` (`approvalProblem`, `app/skills/services/skill-scans.ts`; 409 otherwise): see the skill scanner rule below. The one exception is `DO_NOT_INSTALL` itself, which the admin may override for one copy with a written reason (`overrideReason`, `SKILL_OVERRIDE_REASON`, kept on that copy, so its next version is blocked again); a copy not scanned whole never is (422 with a reason). Only that job and `node ace skills:refresh` call skills.sh and GitHub; no request handler does. From the project's package diagrams, `renderDependencyCruiser` (`src/render/architecture-boundaries.ts`) also renders a `.dependency-cruiser.cjs` (kind `config`, a managed block in `SLASH_MARKERS`) whose `forbidden` rules refuse the dependencies no arrow draws, and adds the command that checks it to the `Architecture` section. A diagram holds no folder path, so a package's name is read as its folder from the repository root, under its parent package's folder when nested; a package whose name is not a plain folder path is left out, a diagram without an arrow between two folders too, and other diagram kinds are not read. Generated files themselves are never committed here (see Authorship). In `apps/api`, the `app/agent-configs/` domain stores what the files are rendered from (the ready-made rules held, the owner's own rules, notes, targets) and immutable generations; every render goes through `render` in `app/agent-configs/services/agent-context.ts` (current catalog), and every change to that source bumps the configuration's `revision` (`bumpRevision`). Never store or edit a generated file outside a generation, and never let an input carry `MARKER_PREFIX`.
- **Agent roles: `packages/catalog/src/roles/`.** A role (a mission, the folders it works in, its rights) is rendered once per target tool that can run one, into a file managed whole (kind `role`: the whole file is its block, no markers). A right is `enforced` only when the tool's documentation (its template's `sources`) establishes that the tool refuses it by itself; otherwise it is an `instruction` written in the role's text. The ready-made roles come from agency-agents at one pinned commit, copied by hand with `node packages/catalog/scripts/vendor-agency-agents.mjs <sha>` (never in CI or tests); re-read `READ_ONLY_PRESETS` against the new missions at every copy. In `apps/api`, roles live in `agent_config_roles` behind the `agent-roles` flag (`FeatureFlagKey.AgentRoles`, 404 while off), and a role is stored only after it passes the catalog's `roleSchema` (422 otherwise), with a `bumpRevision` like any other change to a configuration's source.
- **Sandboxed development container: `packages/catalog/src/render/sandbox.ts`.** Rendered only for the `security.sandbox` rule `container`: `.devcontainer/devcontainer.json` (JSON, merged by the CLI) and `.devcontainer/init-firewall.sh` (a block in `HASH_MARKERS`, run with `bash`, so it needs no executable bit). The firewall is an allowlist whatever the rules held (a test renders every combination): a host is added to a fixed list, per tool in its template's `sandbox` entry, never taken from a text typed into a rule, and nothing is ever forwarded from the host (no credential, agent or socket mount, no `localEnv`). The image is pinned by tag and digest and each tool's CLI to an exact version; after changing either, or the script, start the container (`devcontainer up`) and check that the script ends with its "Firewall ready" line, that a blocked host stays blocked and that `sudo -n true` fails inside.
- **CLI: `apps/cli`.** `@coreloom-uml/cli` is the only package published to npm (`publishConfig.access: public`, versioned on its own outside the changesets `fixed` group, published by `changesets.yml` when `NPM_TOKEN` exists). It is bundled by tsup into one ESM file for Node 22+; `@coreloom-uml/catalog` and `@coreloom-uml/codemap` (devDependencies) and zod are bundled in, so its runtime dependencies stay `citty` and `@clack/prompts`, and it never imports `apps/api` or `ai`. It authenticates with an account API key (`clu_…`, `read` is enough, `write` for `map push`) read from `CORELOOM_UML_API_KEY` or the user config file written by `config set-key` (mode 0600), never from an argument or the manifest; there is no default API URL. It writes only the managed block (`findManagedBlock`/`hashManagedBlock` from the catalog; `#` markers at the top of a TOML settings file, `//` markers in a `.cjs` configuration file, `#` markers in a Git hook or a workflow; for a hook it also writes the `#!` line of a file it creates and adds the execute bits, and it never changes Git's configuration) or, in a JSON settings file, only the entries the generation lists, recorded in the manifest (`src/json-settings.ts`), asks before any change to a settings or `.cjs` file, a hook or a workflow, checks every path the API sends (relative, normalized, inside the working directory, no symbolic link), and leaves a block edited by hand alone unless told otherwise (exit code 2). `check --conformance` (`src/check-conformance.ts`) reads `GET /projects/:id/code-maps/conformance` (the newest ready map, `--map`, or the one `--push` just sent) and exits with 5 when a finding reaches `--fail-on` (`error` by default); it never sends code or calls a model, and with `--json` everything but the object goes to stderr. `map push` (`src/map-push.ts`) runs graphify on the working directory with `GRAPHIFY_BACKEND=none`, its query log off and no variable that looks like a key (`graphifyEnv`), turns the graph into a `CodeMap` with `importGraphify` on the machine and uploads only that, gzipped, as the API's multipart form; it reads the Git remote, branch and commit to label the map, and never keeps a user name or token from the remote URL (`remoteWebUrl`). Programs (`git`, `graphify`) are started without a shell through a `CommandRunner` (`src/run-command.ts`). Everything it prints or asks goes through `Io` (`src/io.ts`) so commands are tested as functions, against a fixture HTTP server, a temporary folder and a fake `CommandRunner`.
- **Calls with the user's own LLM key or subscription: `packages/llm`.** `@coreloom-uml/llm` wraps the Vercel AI SDK (`ai` 7 and the `@ai-sdk/*` providers, exact versions) for the agent-conventions feature: building a model from the browser's provider settings (`createLanguageModel`, redirects never followed), the base URL allowlist (`baseUrlProblem`, from `LLM_ALLOWED_BASE_URLS` in `config/llm.ts`), the connection test and the rule proposals (structured output, then cleaned and deduplicated), and the two subscription models: `openai-codex` (ChatGPT, OpenAI's device code, `codex.ts`) and `claude-code` (Claude, through the `claude` binary, `claude-code.ts`). Packaged like `packages/catalog` (TypeScript source, `.ts` imports); the CLI does not depend on it. API keys stay in the browser only: a key arrives in the request body, is passed to `LanguageModels.create` (`app/llm/services/language-models.ts`) and dropped — never stored, logged, traced, returned or put in an error. The only stored LLM secrets are ChatGPT subscription tokens, encrypted with `APP_KEY` in `llm_connections` (`app/llm-connections/`), under the same never-returned/logged/traced rule. Claude credentials are never handled by our code: only the unmodified `claude` binary (pinned in the API image) holds them, in its own `CLAUDE_CONFIG_DIR` per account; no OAuth flow of ours, and nothing that poses as Claude Code (client id, identity prompt, User-Agent, billing header). Each subscription kind is behind its feature flag, and every call resolves its credential through `resolveCredential` (`app/llm-connections/services/llm-credential.ts`). Every provider failure is reduced to a `LlmFailureReason` before it is logged or answered (502 `{ reason }`). The assistant's chat can stream (`onChunk` on `chatWithAssistant` and `runAssistantTools`, `completeText` and `assistantEventStream` in `src/assistant-stream.ts`): the API answers the AI SDK's UI message stream when the request accepts `text/event-stream` (`answerChat` in `app/assistant/services/chat-answer.ts`, JSON otherwise), and only the chunks `completeText` builds by hand leave it: the text, where each step starts and ends, and a tool's name, never its input or result (the source a repository tool read, the account's data); never pipe `toUIMessageStream()` instead. Beside them, `actionTools` (`followed`, `app/assistant/actions/registry.ts`) writes one `data-activity` part per tool call for the owner to follow the reply as it is made (`ToolActivity`, the same `id` replacing the one before): the tool's name and whether it still runs and, for a repository tool only, what it asks of the sandbox through `show` (a path, a query, a commit, the model's command) and what a command printed, sent as it comes (`liveOutputMs`). Keep it to that: never the input or the result of a tool that reads the account's data, never the text of a file a tool read. An activity goes to the owner's screen only: never stored, logged or traced, and gone once the reply is stored (the web shows it from the `Chat`, `AssistantActivity`). It ends with one `data-chat` part (the JSON route's answer) or one `error` whose text is `{ status, body }`; the owner going away (Stop) aborts the call and stores nothing. A model that answers whole (`claude-code`, and `openai-codex`, whose `codexFetch` reads the endpoint's stream back into one answer) is wrapped in `simulateStreamingMiddleware`. Tests never call a provider: they swap `LanguageModels`, `CodexOAuth` (a fake OAuth server) and `ClaudeCodeCli` (a fake binary) in the container. In `apps/web`, the provider and its key (none for a subscription) live only in the browser (`localStorage` key `llm-provider`, read and written through `src/lib/llm-provider.ts`) and travel only in the body of those calls; the provider kinds, their model suggestions and the allowed origins come from `GET /llm/providers`, never from importing the catalog.
- **Web research: `app/research/` and `packages/llm/src/research.ts`.** Agent conventions made from web pages (`POST /agent-configs/:id/research`, behind the `web-research` flag and `E2B_API_KEY`, 404 without either). Two stages with two levels of trust, kept apart: the research (`researchWeb`) has tools and reads untrusted pages, so the model gets the owner's request and nothing of the configuration; the proposals (`importAgentFile` with `origin: 'research'`, through the existing imports route) read the configuration and have no tool. Never give the research anything private, and never give the import a tool. The tools run in one E2B sandbox per research (`ResearchSandbox`, `app/research/services/research-sandbox.ts`, with `RepositorySandbox` (`app/assistant/services/repository-sandbox.ts`), the only files that import `e2b`; swapped in tests, which never reach E2B): it gets no environment variable and no file of ours, the LLM key never enters it, a URL or the model's command reaches its shell only as an environment variable of one fixed command line, and it is killed in a `finally` (E2B ends it by itself after `RESEARCH_SANDBOX_TIMEOUT_MS` otherwise). `sources` are the pages the sandbox read, never what the model says it read. The HTML a sandbox fetched is reduced to text by `pageFromHtml` (`page-text.ts`), a pure function that executes nothing and walks the text once: keep it free of expressions that can rescan (a test times a hostile page). The request, the URLs, the pages and the findings are never stored or logged, counts only, with two exceptions. A research launched from the assistant hands `conversation` to the imports route, which then stores the exchange in that assistant conversation (`assistant_messages.proposals`): the request, the rules proposed and the addresses of the pages read, never a page, the findings or the `evidence` of a ready-made rule (it quotes the findings), until the conversation is deleted. That path needs both `diagram-assistant` and `web-research`. An assistant conversation belongs to the account and outlives the architectures its messages were about (`assistant_messages.architecture_id`, set to null): the trigger `assistant_forget_architecture` empties `before` and `after` of the changes proposed for an architecture when it is deleted, so no diagram outlives its architecture; keep any new place that stores diagram content in a message under that trigger. - **Skill scanner: `infra/skill-scanner/`.** Each copy of a skill is scanned by NVIDIA's SkillSpector (a Python program, static analysis only) in the API's own queue worker, in an image of its own: stage `skill-scanner` of `apps/api/Dockerfile` (the `runtime` image plus SkillSpector from its source at one commit, its dependencies from `infra/skill-scanner/requirements.lock` with their hashes, Python 3.12 from uv, run as `node`), service `skill-scanner` of every compose file (behind the `skills` profile locally), image `coreloom-uml-skill-scanner` built by `release.yml`. It runs `queue:work --queues=skill-scans` and nothing else; every other worker names its queues without `skill-scans` (the `queue:work` script, the `queue-worker` services), since no other image holds the binary: keep those lists in step with `config/queue.ts`. Its job (`ScanSkillVersionJob`, queued by each skills refresh for the pending copies without a verdict or whose scan failed, `queueSkillScans`) reads the copy from Drive, never from GitHub, and `scanSkillVersion` writes it to a temporary folder and runs `skillspector scan <folder> --no-llm --format json --output <report>` through `SkillScanner` (`app/skills/services/skill-scanner.ts`): no shell, an environment of `PATH` and `HOME` only, killed after `SKILL_SCAN_LIMITS.timeoutMs`; the report is read back through `readScanReport` (a zod schema of the fields read, findings bounded and cut) and stored in `skill_versions.scan`, a scan that gives no verdict as `failed` with its reason. Never run it with `--llm` or give it a model key, never give the service a secret it does not need (its own `APP_KEY`; no GitHub, E2B, account or mail setting), and never let a request handler run it. Tests swap `SkillScanner` and read a real report (`tests/fixtures/skillspector-report.json`); they never start the binary. Raising SkillSpector's version follows `infra/skill-scanner/README.md` (commit, lock, `SKILLSPECTOR_TESTED_VERSION`, a real scan of a known-bad skill, the fixture).
- **Code maps: `packages/codemap`.** `@coreloom-uml/codemap` holds the `CodeMap` format (`codeMapSchema`, checked with `parseCodeMap` before anything stores a map): nodes with a stable `key` (the path for a file, `path#Name` for a symbol, `path#Class.method` for a method, `module:name` for an outside package; a folder is linked as `path/`), edges (`contains`, `imports`, `calls`, `extends`, `implements`, `references`) and a header (extractor, commit, counts). A map holds names, paths and links only, never source code. Extractors are behind importers: `importGraphify` reads graphify's `graph.json` (`schema_version` 1, tested with `graphifyy` `GRAPHIFY_TESTED_VERSION`), reads only the documented fields (never the `_`-prefixed ones), refuses an unknown schema version and keys nothing on graphify's ids. Entry points (`detectEntryPoints`), the matching of a diagram against a map (`matchDiagram`) the processes no diagram covers (`findUncoveredFlows`) and the weight of each match finding (`MATCH_FINDING_LEVELS` in `src/conformance.ts`: `error` when the code contradicts the diagram, `warning` when the diagram is behind the code; an undocumented process is never weighed) are pure functions with no model call: same input, same output. `GET /projects/:id/code-maps/conformance`, the MCP conformance tools and `check --conformance` all read those weights and sentences (`describeMatchFinding`) from there, so they never disagree. Packaged like `packages/uml` (zod only, TypeScript source, `.ts` imports, erasable syntax), in the changesets `ignore` list. The tests read real graphify output from `fixtures/` (see its README to regenerate it); a new framework convention for entry points comes with a fixture case. In `apps/api`, `app/code-maps/` stores them: the `code_maps` row is the header only and the map is a gzipped file in Drive (`services/code-map-storage.ts`, inflating always capped by `CODE_MAP_LIMITS.inflatedBytes`), written only after `parseCodeMap` or `importGraphify` accepted it; deleting a map, a project or an account deletes the files too, since the cascade cannot reach them. `diagram_code_links` hold the owner's decisions per diagram and code key, never per map. These routes never call a model. Drawing from a map does, with the owner's own model: a process (`CodeMapProcessProposalsController`), a proposal (`CodeMapSuggestionDraftsController`) and a message of the assistant sent with `codeMapId` (`answerFromCode` in `app/assistant/services/code-request.ts`, which first names the code a free request is about with `resolveDiagramRequest`). The last two read the map through `drawingSource` (`app/code-maps/services/drawing-source.ts`); all three store the view as a pending assistant change, never as a diagram. Before a sequence, activity or class diagram is drawn, `readSource` (`app/code-maps/services/code-source.ts`) reads the files of the nodes at the map's commit, within `SOURCE_LIMITS`, and hands them to that one call. It reads them in a `RepositorySandbox` of its own, never from this server: the sandbox fetches that one commit (`CLONE_AT`, which needs the full commit id) and each file is one run of `READ_FILE` (a whole text file, cut one byte past `GITHUB_SOURCE_LIMITS.fileBytes` so a larger one is left out), then the sandbox is killed in a `finally`. Given an explorer (`sourceExplorer`, null for `openai-codex`, which carries no tool call), the owner's model then looks at the repository by itself before that call (`exploreSource`, `packages/llm/src/source-exploration.ts`, within `SOURCE_EXPLORATION`): `readSource` cuts the sandbox off the network (`isolate`; no exploration when E2B does not confirm it), the model runs commands of its own through `SHELL` with no token, and what they printed joins the excerpts as sources named by their command: the real output, never what the model says it saw. It never throws and never fails the drawing; the stored answer says how many commands ran. The source is never stored, logged, traced or returned, and a map still holds none. Anything else that needs to look at source code goes through a repository sandbox too: never add a read of a repository's files from the API. A read that fails never fails the drawing, which then goes on from the structure and says why (`sourceSentence`). The conformance review (`app/code-reviews/`, one call of the owner's model per diagram) reads the source the same way, under the same rule, only in a review started with `includeSnippets` and only for `SOURCE_REVIEW_KINDS`; an activity diagram is anchored to the code by its links alone (`matchDiagram` proposes functions for its actions by name and never reports one it does not find), so its conditions and order are checked by that review only, never by the deterministic match; each diagram of the review keeps what was read (`source`: files, left out, or why none), never the code.
- **Code maps from GitHub: `app/code-maps/services/code-map-extraction.ts`.** The server never clones or reads a repository itself: `mapRepository` (called by `ImportGithubCodeMapJob` only, queue `code-maps`) opens one `RepositorySandbox` per import, the assistant's own sandbox class, runs two fixed command lines of `repository-commands.ts` in it (`CLONE` with `REPO_DEPTH=1`, then `MAP`: graphify on the clone with `GRAPHIFY_BACKEND=none`, tree-sitter only, no model), reads back the gzipped `graph.json` `MAP` left beside the clone (`readFile`, size checked in the sandbox, again in the API, then inflated under `CODE_MAP_LIMITS.inflatedBytes`) and kills the sandbox in a `finally`. Only that graph leaves the sandbox: never a file of the repository, and no output of graphify. A private repository's installation token goes to the clone's environment only (`tokenEnvs`, `GIT_CONFIG_*`), never to `MAP`: graphify reads code that may be hostile, so keep the two runs apart. There is no Python and no analyzer service in the repository any more, and no other way to map a repository on the server: E2B is a prerequisite of a deployment (`E2B_API_KEY`, required by the staging and production compose files; without it importing from GitHub answers 503). Repository sandboxes start from an E2B template of ours (`REPOSITORY_TEMPLATE`, `app/assistant/constants/repository.ts`: the install's `base` template plus graphify pinned to `GRAPHIFY_TESTED_VERSION`), built on the install by `node ace assistant:setup` when it does not hold it yet (`RepositorySandbox.ensureTemplate`; a failure is logged and never stops the start). Its name carries the graphify version and `revision`: raising `GRAPHIFY_TESTED_VERSION` builds a new template at the next start, and any other change to the recipe needs `revision` raised. The limits of an import are `GITHUB_IMPORT_LIMITS` and `REPOSITORY_SANDBOX.cloneMaxBytes`; an exit code means one thing whichever line answers it (`MAP_EXIT`, 124 a timeout, `goneExitCode` a sandbox that stopped answering, which is tried again). `tests/unit/assistant/repository-commands.spec.ts` runs `MAP`, `CLONE_AT` and `READ_FILE` with this machine's bash, git and the pinned graphify (CI installs it; skipped locally without that version), and the tests swap `RepositorySandbox` for `FakeMapSandboxes` (`tests/helpers/fake-map-sandbox.ts`, the import job) or `FakeSourceSandboxes` (`tests/helpers/fake-source-sandbox.ts`, `readSource`). After changing `CLONE`, `MAP` or the template, run one real import against an E2B install (`infra/e2b/` locally) before relying on it: only that shows a template without free disk or memory.
- **GitHub App: `app/github/`.** Private repositories reach code maps only through the GitHub App, set by six `GITHUB_APP_*` variables (`githubAppConfig()`, null and every App route 404 while one is missing). Every call to GitHub goes through `GithubApi` (`services/github-api.ts`, swapped in tests: never call GitHub from a test) and is reduced to a `GithubFailure`. The server stores no GitHub token: a connection trades GitHub's `code` (with a `state` from `createGithubState`, bound to the user) for a user token that is used once to list the repositories the user reaches through the App and revoked; only that list is kept (`github_repository_grants`, replaced whole on each connection, pruned by webhooks). `ImportGithubCodeMapJob` makes an installation token for one repository with `contents: read` when the map's owner has a grant on it, hands it to the sandbox's clone (`mapRepository`) and revokes it afterwards: never put one in a job's data, a row, an error or a log. `readSource` makes the same kind of token for one read (`repositoryToken`, `services/repository-token.ts`, shared with the job), gives it to the sandbox's fetch of the commit only and revokes it in a `finally`; since a grant is only what GitHub listed on the day of the connection, it first asks GitHub whether that login still reads the repository (`GithubApi.canRead`) and reads nothing otherwise, dropping the grant on a no; a repository without a grant is fetched with no token. `GithubApi` reads no file: asking GitHub who reads a repository and making tokens is all it does for the source. `POST /github/webhook` checks `X-Hub-Signature-256` over `request.raw()` before reading anything; its work runs on the `code-maps` queue (`FollowGithubPushJob`). A project follows at most one repository (`github_code_map_follows`), and a push is acted on only while the follow's owner still has a grant on it.
- **MCP server: `app/mcp/`.** `/mcp` (`apps/api`) is a Model Context Protocol endpoint for coding agents, built on `@modelcontextprotocol/sdk` (Streamable HTTP, stateless, JSON answers: one `McpServer` and one transport per request, see `mcp-controller.ts`). API tokens only (`guards: ['api']`), behind the `mcp-server` flag (404 while off); the controller checks the `read` ability itself, since every MCP call is a POST and `tokenAbility` reads the method. The controller relays the SDK's own status and body with `response.status(...).send(...)`: the one exception to the typed-helper rule, since the protocol decides the answer and the web client never calls this route; its guard answers (401, 403, 404, 405) still use the typed helpers. The tools (`services/mcp-server.ts`, names in `McpTool`, zod argument shapes in `validators/mcp-input.ts`, a tool that writes taking the bounds of the matching route from the same constants) read, but for the one below that stores a proposal, never call a model, and reach only what the token's account owns (agent conventions by `configId` or by `projectId`, so conventions outside any project are reachable): something that isn't the caller's is a `not found` tool error. `get_code_conformance` and `list_undocumented_processes` (`services/mcp-code-conformance.ts`, `CODE_MAP_TOOLS`) are only listed while the `code-maps` flag is on for the account too: they read the open findings of the newest review of each diagram and the deterministic match against the project's newest ready map (`app/code-maps/services/code-conformance.ts`, shared with the routes). A tool that writes needs the `write` ability and must store a proposal for the owner to review, never apply it: it is listed only to a token that has it (`WRITE_TOOLS`, the `write` option of `buildMcpServer`, read by the controller from the token), so for any other a call is the SDK's own tool error, like a tool behind an off flag. The first is `propose_decision` (with `design-records` too): a coding agent that had to go against the recorded design, or took a structuring decision nothing records, stores a decision through `createDecision`, always `proposed` with `origin: agent` whatever it sends, refused as a tool error when it does not hold together, at most `AGENT_PROPOSALS_WAITING_MAX` waiting per project; its `supersedesId` names the standing decision it says no longer holds and changes nothing. The catalog only recommends how to register the server in each tool (`packages/catalog/src/targets/mcp.ts`); it never renders a tool's MCP settings file.
- `apps/web` talks to the API through the Tuyau typed client (`apps/web/src/lib/client.ts`), whose types come from `@coreloom-uml/api/registry` — generated into `apps/api/.adonisjs/client/registry/` by the assembler hooks in `apps/api/adonisrc.ts` on `node ace serve` / `pnpm dev`. That directory is committed (git-tracked despite `.adonisjs/` being ignored) so `check-types` is deterministic without a prior dev-server run; regenerate and commit it whenever routes, Vine input validators, or controller response shapes change. Return responses from controllers with the typed helpers (`response.ok`, `response.created`, `response.badRequest`, …), never `response.status(x).json(...)`, or the generated response/error types will be wrong.
- In `apps/web`, anything that varies per deployment (currently just the API URL) is resolved at **runtime**, not from `import.meta.env.VITE_*` at build time. The container entrypoint (`apps/web/docker/30-render-env-js.sh`) writes `$API_URL` into `/env.js`, loaded by `index.html` before the bundle; `client.ts` reads `window.__APP_CONFIG__.apiUrl` first, then falls back to `import.meta.env.VITE_API_URL` (dev only), then localhost. Add new runtime settings to all four spots (`public/env.js`, the entrypoint, the `Window` type in `vite-env.d.ts`, the reader) — do not reintroduce build-time `VITE_*` for deploy-varying values.
- In `apps/web`, all API reads and writes go through TanStack Query hooks (`useQuery` / `useMutation`) that wrap the Tuyau `client` — never raw `fetch` or `useEffect` data loading. One exception: a Server-Sent Events stream, which Tuyau cannot open, is read with an `EventSource` in a hook that only invalidates queries when an event arrives (`useSkillsLiveUpdates` in `apps/web/src/lib/skills.ts` is the reference); the data itself still comes through the query hooks. A second one: the workspace assistant's plain message (`POST /assistant/conversations/:conversationId/messages`) is sent with the AI SDK's `useChat` (`@ai-sdk/react`, the way coreloom-ui's AI blocks expect), through a `Chat` per conversation (`createAssistantChat` and `sendChat` in `apps/web/src/lib/assistant-chat.ts`, called from the `useAskAssistant` mutation) that reads the API's UI message stream; the `Chat` only holds the reply being written and is emptied once it ends, and the stored messages still come back through the query hooks. The shared `QueryClient` and the canonical hook pattern to copy live in `apps/web/src/lib/query.ts`; `apps/web/src/auth/auth-context.tsx` is the live reference (`useQuery` for `GET /auth/me`, `useMutation` for login/register/logout, `refresh` = `invalidateQueries`). Its `useAuth()` return surface (`user`, `isLoading`, `login`, `register`, `logout`, `refresh`) is a stable contract — keep it.
- In `apps/web`, forms use TanStack Form through coreloom-ui's `useAppForm` (`@/components/ui/form`: `form.AppField` + `field.TextField` / `PasswordField` / `SelectField`…, `form.SubmitButton`), validated with a `zod` schema in `validators.onSubmit`. Password length comes from `@coreloom-uml/auth-policy` (`PASSWORD_POLICY.minLength`). A page that delegates to a coreloom-ui block (`LoginForm`, `SignupForm`, `PasswordResetForm`, `SettingsSection`…) passes props in and leaves the block's own field handling alone.
- In `apps/web`, every user-facing string the app adds lives in `apps/web/src/messages.ts` (`en` is the source of truth and defines the `Messages` type; `fr` is translation data, so the English-only rule does not apply to its values) and is read with `const t = useT()` (`@/lib/locale`). Components' built-in strings come from coreloom-ui's `CoreloomI18nProvider`, which `LocaleProvider` feeds with the same locale (`useCoreloomI18n().messages` for things like `diagram.kinds`). No literal copy in JSX, no i18next. The language is a browser preference in `localStorage`, not deploy config.
- `apps/api` observability is OpenTelemetry → SigNoz in `apps/api/instrumentation.ts`, loaded before everything else via `node --import ./instrumentation.js` (prod `start` script + Dockerfile `CMD`) and re-imported in `bin/server.ts` for the shutdown flush. It reads the standard `OTEL_*` variables straight from `process.env` (it runs before `start/env.ts`), and is a no-op unless `OTEL_EXPORTER_OTLP_ENDPOINT` is set — so do **not** add `OTEL_*` to `start/env.ts`.
- The staging Coolify stack (`infra/docker-compose.staging.yml`) bundles a self-hosted SigNoz (`signoz-clickhouse` / `signoz-zookeeper` / `signoz` / `signoz-otel-collector` + migrators); the `api` service exports to `signoz-otel-collector:4318` over the Compose network. `infra/signoz/*` is a vendored copy from SigNoz `deploy/` at tag `v0.128.0` (the last tag with a Compose manifest) — re-copy from that tag rather than hand-editing. Keep the four image pins in the compose file in sync with that tag's manifest.
- Security headers: `@adonisjs/shield` (`apps/api/config/shield.ts`) for the API — `xFrame`/`hsts`/`contentTypeSniffing` on, `csp`/`csrf` intentionally off (JSON API; CORS allowlist + forced JSON preflight is the CSRF boundary). The SPA's `Content-Security-Policy` and hardening headers live in `apps/web/docker/nginx.conf.template`, where `${API_URL}` scopes `connect-src`.
- Email addresses are case-insensitive: `users.email` is `citext` (migration `1714000002000`) and every VineJS email input ends with `.toLowerCase()`. Keep both in sync — new email fields get `.toLowerCase()`, and don't reintroduce a plain `varchar` email column.
- `middleware.verified()` (`apps/api/app/auth/middleware/verified-middleware.ts`, registered in `start/kernel.ts`) gates a route behind a verified email — chain it after `middleware.auth()`. Nothing uses it yet; wire it onto routes that need it rather than re-checking `emailVerifiedAt` inline.
- Outbound transactional email is always `mail.sendLater(...)`, never `mail.send(...)`, so SMTP latency/failures never block or fail the request. `apps/api/start/mail.ts` registers a `mail.setMessenger` that turns every `sendLater` into a `SendMailJob` on the BullMQ queue — the send is retried on failure, visible/replayable in bull-board, and `SendMailJob.onFailed` logs a send that exhausts its retries. Do not add per-call-site `try/catch` + `logger.error`, and do not reach for `mail.send()` in a controller.
- File uploads go through `@adonisjs/drive` (never the DB, never the public filesystem), validated for MIME/extension **and** size at the boundary via `request.file(field, { size, extnames })` + `file.isValid`/`file.errors` → 422 — see `apps/api/app/account/controllers/avatar-controller.ts`, allowlist + max size as an `as const` in `app/account/constants/avatar.ts`. The disk is `private`: serve private objects back through an authenticated route that streams `disk.getStream(key)` with the right `Content-Type` (e.g. `GET /account/avatar`), not a signed URL. `serializeUser` stays **synchronous** and returns that stable relative path (`avatarUrl: user.avatarKey ? '/account/avatar' : null`) — do not make it async to build a signed URL.

Job classes live in `app/jobs/*_job.ts` (`node ace make:job`, one `default`-exported class extending `Job<Data, Return>` with a `process()` method), dispatched with `SomeJob.dispatch(data)` from a controller/service and executed by the `queue:work` worker (its own process — `pnpm --filter @coreloom-uml/api queue:work` locally, the `queue-worker` service in staging). `apps/api/app/jobs/example_job.ts` is the reference — copy it. Inspect / retry / remove jobs in `bull-board` (`http://localhost:8082` in dev). `apps/api/start/mail.ts` already routes `mail.sendLater(...)` onto this queue via `SendMailJob`, so transactional email is queued end to end.
